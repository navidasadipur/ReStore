## Step 1 decisions

- Catalog prices, API product inputs and new order amounts are integer IRR (rials).
- Display divides rials by 10 and formats Persian digits with the toman suffix.
- Admin price input is explicitly labelled rials; it sends the stored integer unchanged.
- Delivery costs 500,000 rials (50,000 tomans); free delivery applies strictly above
  10,000,000 rials (1,000,000 tomans), not at the threshold.
- Server payment/order totals use StoreMoney.GetDeliveryFee; frontend uses the same policy.
- Order details display the stored delivery fee, never today's shipping policy.
- All orders use IRR, including existing demo orders after repricing. There is no per-order currency field or USD display mode.
- New Stripe intents and updates are disabled with a clear checkout error until ZarinPal is connected.
  Signed Stripe webhook processing remains available for historical orders.

## Database upgrade

Migration 20261102090000_UseIranianRialCatalog deliberately reprices the entire existing
**demo catalog**, including any edited products: old Price * 1,000 becomes the new rial
price. This is sample pricing, not an exchange rate; existing catalog and orders are assumed to be demo data.
For example, a board formerly priced at 20,000 USD cents ($200) becomes 20,000,000 rials
(2,000,000 tomans). Fresh databases seed the same rial prices. Existing demo order item
prices, subtotals and saved delivery fees are also multiplied by 1,000 so every stored
amount uses rials. Saved delivery fees are preserved under this repricing rule, not
recalculated using the current free-delivery policy.

The migration also clears basket Stripe intent IDs/client secrets so old USD intents cannot
be reused. Historical order payment IDs remain intact; all order amounts become rials.
There is no automatic refund or cancellation of external Stripe intents in this step.

Review these demo prices before applying to a non-demo catalog. Database initialization
runs migrations at API startup: back up an existing database before running the updated API.
Rollback requires restoring the backup; Down intentionally refuses to divide newly
entered rial prices blindly.

No database upgrade or deployment has been performed as part of editing this code.

## Step 2 configuration

The server validates ZarinpalSettings during infrastructure registration, before database
initialization. Mode must explicitly be Sandbox or Production; unrecognized values never
fall back to live payments. MerchantId must be a non-empty UUID. CallbackUrl must be an
absolute HTTP(S) URL with no embedded credentials or fragment. HTTP is accepted only for
loopback callbacks in Sandbox; Production requires HTTPS and a non-loopback host and
rejects the checked-in test merchant. Validation checks configuration syntax, not whether
ZarinPal has activated the merchant or the callback domain matches the panel.

The checked-in defaults are Sandbox, test merchant
11111111-1111-4111-8111-111111111111, and
http://localhost:5000/checkout/result. The sandbox permits an arbitrary
UUID according to [ZarinPal's sandbox documentation](https://www.zarinpal.com/docs/paymentGateway/sandBox).
The base host is derived exclusively from Mode: https://sandbox.zarinpal.com/ or
https://payment.zarinpal.com/, following the
[official connection guide](https://www.zarinpal.com/docs/paymentGateway/connectToGateway).
No request is sent in this step.

For local testing, the defaults need no changes. If using a different API port, override:

~~~powershell
$env:ZarinpalSettings__CallbackUrl = 'http://localhost:5001/checkout/result'
~~~

Production requires all three overrides, supplied by the deployment environment:

~~~powershell
$env:ZarinpalSettings__Mode = 'Production'
$env:ZarinpalSettings__MerchantId = '<merchant-UUID-from-ZarinPal-panel>'
$env:ZarinpalSettings__CallbackUrl = 'https://your-domain.example/checkout/result'
~~~

Replace the placeholders before startup. Do not put real credentials in committed JSON or
browser configuration. ASP.NET Core environment variables and user secrets override the
checked-in values. The selected mode appears in the startup log, without the merchant ID.

To review validation without starting the API or applying migrations:

~~~powershell
dotnet test Test/ReStore.Test/ReStore.Test.csproj --configuration Release --filter FullyQualifiedName~ZarinpalSettingsTests --no-restore --disable-build-servers -m:1 -p:UseSharedCompilation=false
~~~

The tests load the actual checked-in JSON, check both environment hosts and DI overrides,
and reject malformed modes, merchants and callbacks before database or network access.
The Sandbox callback endpoint is available in step 6. The storefront calls it in step 7.

Step 2 verification: all 160 backend tests passed, including 23 ZarinPal configuration cases. The API compiled successfully. No API startup against the configured database, database migration, external payment request or deployment was performed.

## Step 3 payment attempts

Migration 20261115090000_AddPaymentAttempts adds the PaymentAttempts table. Each row
stores the order ID, amount in rials, Sandbox flag, status, creation time in UTC,
optional Authority and optional RefId. Authority can be assigned after a request to
ZarinPal. The same Authority is unique within each environment.

An order may have multiple attempts. A filtered unique index permits at most one
successful attempt per order. The database rejects nonpositive amounts and prevents
deletion of orders referenced by attempts. Existing orders have no new payment
attempts until checkout creates them in a later step.

## Step 4 pending orders

Send an authenticated POST to /api/orders/pending with a new UUID in
checkoutRequestId, shippingAddress, and optional saveAddress. The response uses
the existing insert envelope and returns the order ID in key. Read it through
GET /api/orders/{id} to see Pending status, line items, address and the rial total.

Reuse the UUID when retrying the same submission. Deduplication is scoped to
the signed-in buyer. A replay returns the original order, including when the
basket or the submitted address has changed. Use a new UUID for a new order.

The server snapshots prices and calculates shipping. Creating a pending order leaves
the basket and available stock in place. The migration adds the checkout UUID and
allows new orders to omit their legacy Stripe intent.

## Stock in the Sandbox checkout

On the first successful verification, save the payment reference and mark the order
paid. If all items are still available, deduct their quantities in the same database
transaction. If stock is insufficient, leave stock unchanged and still record the
verified payment. An out-of-stock paid order may require manual handling. Stock
reservation, expiry, and automated handling for that case are outside the current scope.

## Step 5 Sandbox payment link

After creating an order with POST /api/orders/pending, use its key in an authenticated
POST /api/payments/zarinpal/{orderId}. The request has no body. Read data.paymentUrl
from a successful response and open it to reach the Sandbox payment page.

The server uses the saved rial total and stores Authority before sending the URL.
Repeat requests reuse the pending attempt. The endpoint currently accepts Sandbox
configuration. Step 6 adds callback verification and updates the order status.

## Step 6 Sandbox callback

After completing the Sandbox payment, the browser returns to the configured storefront
URL with Authority and Status. The storefront calls GET /api/payments/zarinpal/callback.
The payment result envelope includes orderId,
paid and referenceId. An OK callback asks ZarinPal to verify the saved authority and
rial amount. A NOK callback reports the stored result and leaves an unconfirmed
attempt pending. Reloading a completed callback reads the stored result.

Verification codes 100 and 101 confirm payment. If 101 gives no reference, the order
is recorded as paid with a null reference. The payment attempt, order status and any
stock deduction are committed together. If stock is insufficient, the verified payment
is still saved and stock stays as it was. An unconfirmed response leaves the order
pending for a later retry.

## Step 7 storefront checkout

Run the API against a local PostgreSQL demo database with migrations applied. For the
React dev server, set the callback URL before starting the API:

~~~powershell
$env:ZarinpalSettings__CallbackUrl = 'http://localhost:3000/checkout/result'
~~~

Sign in, add an item to the basket, complete the address and select Pay with ZarinPal.
Complete a test payment and confirm that the result shows the order and reference.
Reload the result page and verify that stock was deducted only once. A cancelled
payment shows an incomplete result. The API retains the basket in this Sandbox flow.
